# Run E2E Flows

Execute E2E test flows against a live Appmixer instance.

## Prerequisites

- `APPMIXER_ENV` environment variable pointing to `.env` file (see below)
- Connector source in `$CONNECTORS_DIR/src/appmixer/<connector>/`
- Test flow JSON files in `artifacts/test-flows/` (generated by `test-flows` skill)
- Appmixer CLI configured (`appmixer url` + login)
- **Stores** `E2E Failed Tests` and `E2E Succeeded Tests` must exist on the Appmixer instance (auto-created by `ensure-stores` command)

**Required: `.env` file**

All configuration is in a single `.env` file. Set `APPMIXER_ENV` to its path before running:

```bash
export APPMIXER_ENV=/path/to/.env
```

The `.env` file must contain:

```
CONNECTORS_DIR=/path/to/appmixer-connectors
APPMIXER_BASE_URL=https://api.appmixer.com
APPMIXER_USERNAME=your@email.com
APPMIXER_PASSWORD=yourpassword
```

| Variable | Description |
|----------|-------------|
| `CONNECTORS_DIR` | Root of the appmixer-connectors repo |
| `APPMIXER_BASE_URL` | Appmixer instance API URL |
| `APPMIXER_USERNAME` | Appmixer login email |
| `APPMIXER_PASSWORD` | Appmixer login password |

`SKILL_DIR` is auto-detected from the script location.

Verify before proceeding:
```bash
: "${APPMIXER_ENV:?APPMIXER_ENV is not set — point it to your .env file}"
test -f "$APPMIXER_ENV" || { echo "File not found: $APPMIXER_ENV"; exit 1; }
source "$APPMIXER_ENV"
: "${CONNECTORS_DIR:?CONNECTORS_DIR missing in $APPMIXER_ENV}"
: "${APPMIXER_BASE_URL:?APPMIXER_BASE_URL missing in $APPMIXER_ENV}"
: "${APPMIXER_USERNAME:?APPMIXER_USERNAME missing in $APPMIXER_ENV}"
: "${APPMIXER_PASSWORD:?APPMIXER_PASSWORD missing in $APPMIXER_ENV}"
test -d "$CONNECTORS_DIR/src/appmixer" || { echo "Invalid CONNECTORS_DIR: $CONNECTORS_DIR"; exit 1; }
```

## Quick Start

For a connector with existing test flows and auth account:

```bash
bash $SKILL_DIR/scripts/appmixer-flow.sh deploy-and-run <connector>
```

This does everything: pack, publish, upload flows, assign accounts, start, wait, show results.

For step-by-step control, see the Workflow section below.

## Modifier Functions (Prefer Over CodeBlock)

Appmixer transforms support **modifier functions** in the `functions` array of a variable reference. These run natively in the engine without needing a CodeBlock component. **Always prefer modifiers over CodeBlock** -- they are simpler, faster, and don't have the `result` wrapping issue.

### Available modifier functions

| Function | Description | Parameters |
|----------|-------------|------------|
| `g_uuid4` | Generate UUID v4 | none |
| `g_timestamp` | Current Unix timestamp (ms) | none |
| `g_now` | Current ISO 8601 date | none |
| `g_addTimeSpan` | Add time to a date | `hashParams: { days: {value: N}, hours: {value: N}, minutes: {value: N} }` |
| `g_random` | Random number (0-1) | none |
| `g_flowName` | Current flow name | none |
| `g_flowId` | Current flow ID | none |
| `g_userId` | Current user ID | none |
| `g_jsonPath` | Extract from JSON via JSONPath | `params: [{value: "$.path"}]` |
| `g_regex` | Regex matching | `params` for pattern, `hashParams` for flags |
| `g_first` | First element of array | none |
| `g_last` | Last element of array | none |
| `g_length` | Length of string/array | none |
| `g_javascript` | Run arbitrary JS code | `params: [{value: "code"}]` |
| `g_stringify` | Object to JSON string | none |
| `g_split` | Split string by delimiter | `params: [{value: "delimiter"}]` |
| `g_add` | Addition | `params: [{value: N}]` |
| `g_mul` | Multiplication | `params: [{value: N}]` |
| `g_floor` | Floor rounding | none |
| `g_greaterThan` | Comparison (greater than) | `params: [{value: N}]` |

### Common E2E patterns using modifiers

**Unique email per run** (instead of CodeBlock):
```json
"email": {
    "email-var": {
        "variable": "$.set-variables.out.emailPrefix",
        "functions": []
    },
    "ts-var": {
        "variable": "$.on-start.out.started",
        "functions": [{ "name": "g_timestamp" }]
    }
}
```
With lambda: `"email": "{{{email-var}}}-{{{ts-var}}}@appmixer-test.com"`

**Future date** (instead of CodeBlock):
```json
"startTime": {
    "start-var": {
        "variable": "$.on-start.out.started",
        "functions": [
            { "name": "g_now" },
            { "name": "g_addTimeSpan", "hashParams": { "days": {"value": 14} } }
        ]
    }
}
```

**UUID as unique identifier**:
```json
"uniqueName": {
    "name-var": {
        "variable": "$.set-variables.out.baseName",
        "functions": [{ "name": "g_uuid4" }]
    }
}
```
With lambda: `"uniqueName": "E2E-{{{name-var}}}"`

### When to use CodeBlock instead

Use CodeBlock only when modifiers can't express the logic:
- Complex string formatting that requires multiple transformations chained
- Conditional logic (if/else)
- Math beyond simple add/multiply
- Parsing complex nested structures

## Flow Completion Detection

Flows are monitored via **log polling**, not flow stage:

- **ProcessE2EResults in logs** = flow completed. The script auto-stops the flow and parses assert results.
- **Component errors in logs** = tracked and reported. OnError/StopFlow component errors are **ignored** (they are noisy infrastructure artifacts).
- The script polls logs every 5 seconds. When ProcessE2EResults is found (without error), the flow is stopped and results are extracted.

Do NOT use `OnError + StopFlow` components in test flows — they cause spurious lock errors on some instances and add noise to logs.

## Workflow

### Step 1: Publish Connector

Pack and publish the connector to the live instance:

```bash
cd $CONNECTORS_DIR/src/appmixer
appmixer pack <connector>
appmixer publish <connector>.zip
```

If `appmixer` CLI is not authenticated, run:
```bash
source "$APPMIXER_ENV"
appmixer url "$APPMIXER_BASE_URL"
echo "$APPMIXER_PASSWORD" | appmixer login "$APPMIXER_USERNAME"
```

### Step 2: Ensure Auth Account Exists

List existing accounts or create one:

```bash
# List existing accounts
bash $SKILL_DIR/scripts/appmixer-flow.sh list-accounts appmixer:<connector>

# Or create from local configstore (appmixer CLI stores auth here after `appmixer test auth`)
CONFIGSTORE="$HOME/.config/configstore/appmixer.json"
AUTH_JSON=$(python3 -c "
import json
d = json.load(open('$CONFIGSTORE'))
fields = d.get('appmixer:<connector>', {}).get('authFields', {})
print(json.dumps(fields))
")
ACCOUNT_ID=$(bash $SKILL_DIR/scripts/appmixer-flow.sh create-account <connector> "$AUTH_JSON")
```

Test the account is valid:
```bash
TOKEN=$(bash $SKILL_DIR/scripts/appmixer-flow.sh auth | tail -1)
curl -s -X POST "$BASE_URL/accounts/$ACCOUNT_ID/test" -H "Authorization: Bearer $TOKEN"
# Should return {"ok":true}
```

### Step 3: Upload Test Flows

```bash
# Upload all test flows at once
bash $SKILL_DIR/scripts/appmixer-flow.sh upload-all \
    $CONNECTORS_DIR/src/appmixer/<connector>/artifacts/test-flows \
    <connector> "$ACCOUNT_ID"

# Or upload a single flow
bash $SKILL_DIR/scripts/appmixer-flow.sh upload-flow \
    test-flow-xxx.json <connector> "$ACCOUNT_ID"
```

Each flow is prepared automatically with:
- `customFields.category: "E2E_test_flow"` -- for filtering
- `description: "E2E test flow"`
- **ProcessE2EResults stores** -- `config.properties.failedStoreId` and `config.properties.successStoreId` are set
- **ProcessE2EResults recipients** -- `recipients` set in the lambda
- **Account** -- `config.properties.account` set on connector components

The upload commands use the createOrUpdate pattern: if a flow with the same name exists, it is stopped and updated in place (with `?forceUpdate=true`). Flows are never deleted and recreated.

### Step 4: Account Assignment (Automatic)

The `upload-flow` and `upload-all` commands automatically assign accounts via the auth API. No manual step needed.

If you need to re-assign accounts manually:
```bash
bash $SKILL_DIR/scripts/appmixer-flow.sh patch-accounts "$FLOW_ID" "$ACCOUNT_ID" "appmixer.<connector>."
```

**NOTE**: Just setting `config.properties.account` in the flow JSON is NOT enough. The auth API call (`PUT /auth/component/:componentId/:accountId`) is required for the engine to find the access token.

### Step 4b: Validate Variable References

After uploading/updating a flow, **validate that all variable references are resolvable** using the variables fetch endpoint. This catches issues like:
- Assert components referencing fields from dynamic output ports (e.g. components with `generateOutputPortOptions`) that only expose `Raw Output`, not individual fields
- Typos in variable paths
- Missing upstream connections

```bash
TOKEN=$(bash $SKILL_DIR/scripts/appmixer-flow.sh auth | tail -1)
BASE="$APPMIXER_BASE_URL"

# Validate all Assert components in the flow
bash $SKILL_DIR/scripts/appmixer-flow.sh validate-variables "$FLOW_ID"
```

Or manually via the API:

```bash
# Fetch available variables for specific components
curl -s -X POST "$BASE/variables/$FLOW_ID/fetch?compress=true" \
    -H "Authorization: Bearer $TOKEN" \
    -H "Content-Type: application/json" \
    -d '{
        "useCache": false,
        "flow": false,
        "components": {
            "IDs": ["assert-create", "assert-update", "assert-find"],
            "properties": true,
            "links": true
        }
    }'
```

**How to interpret the response:**
- `dynamicComponentVariables[]` -- all variables available to the requested components. Each has `componentId`, `port`, `label`, and `value` (the mustache template like `{{{$.comp-id.port.field}}}`)
- `components.<id>.links.in.<sender>.<port>.variables.refs` -- indices into `dynamicComponentVariables` showing which vars are available from that link
- `components.<id>.links.in.<sender>.<port>.variables.errors` -- **if this contains `dynamic` errors, the variable references in that component are INVALID**

**Common issue:** Components with dynamic output ports (like `FindManualJournals` with `outputType: "item"`) only expose `Raw Output` (`{{{$.comp-id.out}}}`), NOT individual fields. Asserts referencing `$.comp-id.out.FieldName` will show as "invalid variable" in the UI and won't receive values at runtime.

**Fix:** If dynamic variables are missing, ensure the component's output port source URL has `ignoreAuth=true` and does NOT pass unused fields (like `tenantId`) in `messages`. After fixing, individual fields become available and MUST be used in asserts.

**NEVER assert on Raw Output** (`$.comp-id.out`) -- Raw Output always contains something, so the assertion is meaningless. Always test specific fields (e.g. `$.comp-id.out.ManualJournalID` notEmpty) to verify the output schema is correctly defined and actual values flow through.

### Step 5: Start and Monitor

```bash
# Run all E2E flows for a connector
bash $SKILL_DIR/scripts/appmixer-flow.sh run-all <connector> 180

# Or run individual flows
bash $SKILL_DIR/scripts/appmixer-flow.sh start "$FLOW_ID"
bash $SKILL_DIR/scripts/appmixer-flow.sh wait-done "$FLOW_ID" 120
bash $SKILL_DIR/scripts/appmixer-flow.sh logs-summary "$FLOW_ID"
```

Look for:
- **Assert results** -- `appmixer.utils.test.Assert` output with `success` and `error` arrays
- **ProcessE2EResults** -- should show recipients and test results (not "Component error")
- **AfterAll** -- aggregated results from all assertions

### Step 6: Fix and Re-run Loop

On failure, the workflow is:

1. **Read error logs** -- identify failing component and error
2. **Fix** -- update component source or test flow JSON
3. **Re-publish** connector if source changed: `appmixer pack && appmixer publish`
4. **Re-upload** flow using the same createOrUpdate pattern (NOT delete+create)
5. **Re-assign accounts** via auth API
6. **Re-start** flow and check results

**Do NOT delete flows between iterations.** Always update in place.

## Known Gotchas

### Stale logs from previous runs
The `run-all` command fetches the last N log entries without strict timestamp filtering. Errors shown may be from **previous** runs, not the current one. Always check `gridTimestamp` when interpreting results. A flow marked "done" with ProcessE2EResults in current-run logs is passing even if old errors appear in the log window.

### BeforeAll is REQUIRED
Every E2E test flow **must** include `appmixer.utils.test.BeforeAll` after OnStart to reset Assert/AfterAll state between runs. Without it, assertion state accumulates across runs and results become unreliable. Pattern: `OnStart -> BeforeAll -> SetVariable -> ... -> AfterAll -> [Cleanup] -> ProcessE2EResults`.

### `GET /flows` default limit is 100
The list flows endpoint returns max 100 results by default. If there are more than 100 E2E flows on the instance, newer flows won't appear. **Always use `limit=500`** in all list queries: `GET /flows?filter=...&limit=500`.

### `GET /flows/:flowId` Elasticsearch errors
The full `GET /flows/:flowId` endpoint (without `?projection=`) can return Elasticsearch errors on some instances. **Always use `?projection=stage` for status checks** and `?projection=flow` when you need the flow definition. The `wait-done` and `get` commands in the helper script already handle this.

### E2E flows don't auto-stop after ProcessE2EResults
After ProcessE2EResults runs, the flow remains in `running` state. The `wait-done` command handles this by checking logs for ProcessE2EResults on timeout and stopping the flow. If manually polling, check logs for ProcessE2EResults presence.

### Search/Find race conditions after Create
Many APIs have eventual consistency on search indexes. A contact or record created 1 second ago may not appear in search results yet. If your test flow does Create -> Find immediately:
- **Best approach:** Search for a pre-existing test record instead of a just-created one
- **Alternative:** Add a `appmixer.utils.controls.CodeBlock` with `await new Promise(r => setTimeout(r, 5000))` as a delay (note: `appmixer.utils.controls.Sleep` does not exist on all instances)
- **Alternative:** Use GetById between Create and Find to add natural delay

### Duplicate records on re-runs
Previous test runs may leave records behind if cleanup failed. Before starting flows:
1. Stop any running flows first
2. Check if the API rejects duplicates (e.g. GHL: "location does not allow duplicated contacts")
3. Clean up leftover test data from previous runs via the connector's API

### CodeBlock output wraps results under `result`
The `appmixer.utils.controls.CodeBlock` component wraps the code's return value under a `result` field. If the code evaluates to `"hello"`, the output is `{ result: "hello" }`. Access it via `$.code-block-id.out.result`. For objects, deep access like `$.code-block-id.out.result.field` does NOT work -- CodeBlock result is opaque. Return simple strings/numbers and use `$.code-block-id.out.result` directly.

### CodeBlock code syntax
CodeBlock runs code in `isolated-vm`. Bare `return` statements are illegal. Use expressions directly (e.g., `'value-' + Date.now()`) or IIFEs (e.g., `(() => { ... return x; })()`). The code must be a single expression that evaluates to a value.

### Flows must be stopped before PUT update
The `PUT /flows/:flowId` endpoint rejects updates on running flows. **Always stop the flow before updating**, then use `?forceUpdate=true` as a safety net. Without this, updates are silently rejected and the old flow definition keeps running.

### Deterministic test design
Tests must pass on repeated runs without input changes. Key patterns:
- **Create + Delete cleanup**: If the API rejects duplicates (e.g., contacts by email, opportunities per contact), the test MUST delete created resources at the end. Add `DeleteX -> ProcessE2EResults` chain.
- **Unique inputs via modifiers**: Use `g_timestamp` or `g_uuid4` modifier functions to generate unique identifiers (e.g., `e2e-{{{ts-var}}}@test.com`). Prefer modifiers over CodeBlock. Only use CodeBlock if modifiers can't express the logic.
- **Avoid hardcoded dates**: Use `g_now` + `g_addTimeSpan` modifier to compute future dates dynamically. Hardcoded dates expire and tests break.
- **Cross-component variable references**: When referencing variables from indirect upstream components (2+ hops), prefer direct upstream references. E.g., use `$.find-items.out.id` instead of `$.create-item.out.id` when the update is triggered by find.

### Log parsing
The `/logs` API returns raw Elasticsearch hits. Error details are in `hits[]._source.err` as a **JSON string** (not object). The `message` field is often empty. Use `logs-summary` command for parsed output, or parse `err.response.data` for the actual error message.

### Special characters in `.env` passwords
Passwords with `&`, `!`, `|` etc. break `source .env`. The helper script uses Python to safely parse the `.env` file, so always use the script commands rather than sourcing the file directly in bash.

### Stores must exist
The `E2E Failed Tests` and `E2E Succeeded Tests` stores must exist. Use `ensure-stores` command to auto-create them if missing:
```bash
bash $SKILL_DIR/scripts/appmixer-flow.sh ensure-stores
```

### `validate-variables` checks structure only
The `validate-variables` command checks that variable paths exist in the flow graph. It does NOT validate runtime data. A variable like `$.codeblock.out.result.field` may pass validation but fail at runtime if CodeBlock wraps the result opaquely. Always test by running the flow.

## Helper Script

`scripts/appmixer-flow.sh` wraps all API calls:

```
appmixer-flow.sh auth                    — Get auth token
appmixer-flow.sh create <flow.json>      — Create flow -> flowId
appmixer-flow.sh get <flowId>            — Get flow details
appmixer-flow.sh start <flowId>          — Start flow
appmixer-flow.sh stop <flowId>           — Stop flow
appmixer-flow.sh delete <flowId>         — Delete flow
appmixer-flow.sh patch-accounts <flowId> <accountId> <prefix>
                                         — Patch flow JSON + assign via auth API
appmixer-flow.sh upload-flow <flow.json> <connector> <accountId>
                                         — Stop + prepare + upload + assign auth
appmixer-flow.sh upload-all <flows-dir> <connector> <accountId>
                                         — Upload all test-flow-*.json files
appmixer-flow.sh run-all [filter] [timeout]
                                         — Start all E2E flows, wait, show summary
appmixer-flow.sh deploy-and-run <connector> [accountId]
                                         — Full pipeline: pack -> publish -> upload -> run
appmixer-flow.sh logs <flowId> [size]    — Get raw logs JSON
appmixer-flow.sh logs-summary <flowId> [size] [since_ts]
                                         — Parsed log summary with errors
appmixer-flow.sh wait-done <flowId> [timeout]  — Poll until done (auto-detects
                                           ProcessE2EResults on timeout)
appmixer-flow.sh ensure-stores           — Create E2E stores if missing
appmixer-flow.sh list-e2e-flows [filter] — List E2E flows (optional name filter)
appmixer-flow.sh create-account <connector> <auth-json>
appmixer-flow.sh list-accounts [service] — List accounts
appmixer-flow.sh validate-variables <flowId> [componentIds...]
                                         — Validate variable refs via fetch API
```

## Key API Endpoints

| Action | Method | Endpoint |
|--------|--------|----------|
| List E2E flows | GET | `/flows?filter=customFields.category:E2E_test_flow&limit=500` |
| Get flow | GET | `/flows/:flowId?projection=flow` (always use projection!) |
| Create flow | POST | `/flows` |
| Update flow | PUT | `/flows/:flowId?forceUpdate=true` |
| Assign account | PUT | `/auth/component/:componentId/:accountId` |
| List accounts | GET | `/accounts` |
| Test account | POST | `/accounts/:accountId/test` |
| Get stores | GET | `/stores` |
| Start flow | POST | `/flows/:flowId/coordinator` `{"command":"start"}` |
| Stop flow | POST | `/flows/:flowId/coordinator` `{"command":"stop"}` |
| Get logs | GET | `/logs?flowId=:flowId&from=0&size=100` |
| Validate variables | POST | `/variables/:flowId/fetch?compress=true` |
